# Monitoring and observability

## The problem

Someone asks which team is spending the most on Claude Code, or whether the MCP server you rolled out last month is being used, or who approved the `Bash` call that touched production. Answering any of them from `/usage` means walking to nine desks. <LessonLink id="I2.1" /> taught you to estimate what a session costs. The estimate stops being enough the moment the question is about other people's sessions.

## The concept

Claude Code speaks OpenTelemetry. Turn on the exporter and every session on every machine emits metrics and structured events to a collector you run, tagged with enough attributes to answer cost questions by user, team, model, and feature.

Two properties shape how you use it. Content is redacted by default, so the exporter gives you shapes and numbers until you deliberately turn on the text. And when an administrator sets the destination in managed settings, Claude Code removes the developer-set variables that would conflict with it, which is what turns a telemetry endpoint into a requirement rather than a suggestion.

## How it works

### Turning it on

The exporter is a handful of environment variables. Nothing is emitted until the first one is set.

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer your-token"
```

`OTEL_METRICS_EXPORTER` accepts `otlp`, `prometheus`, `console`, or `none`, and `OTEL_LOGS_EXPORTER` accepts `otlp`, `console`, or `none`, both comma-separated for more than one destination. The protocol is `grpc`, `http/json`, or `http/protobuf`. Metrics export every 60 seconds and logs every 5 by default, adjustable with `OTEL_METRIC_EXPORT_INTERVAL` and `OTEL_LOGS_EXPORT_INTERVAL`. Each signal can override the endpoint, protocol, and headers on its own with the `OTEL_EXPORTER_OTLP_METRICS_*` and `OTEL_EXPORTER_OTLP_LOGS_*` forms.

Distributed tracing is in beta behind a second flag, `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` plus `OTEL_TRACES_EXPORTER`, and its spans carry W3C trace context headers.

### The metrics

| Metric | Unit | Carries |
|---|---|---|
| `claude_code.session.count` | count | `start_type` |
| `claude_code.token.usage` | tokens | `type`, `model`, `query_source`, `speed`, `effort`, and the feature attributes below |
| `claude_code.cost.usage` | USD | the same set as token usage |
| `claude_code.lines_of_code.count` | count | `type`, `model` |
| `claude_code.commit.count` | count | standard attributes |
| `claude_code.pull_request.count` | count | standard attributes |
| `claude_code.code_edit_tool.decision` | count | `tool_name`, `decision`, `source`, `language` |
| `claude_code.active_time.total` | seconds | `type`, either `user` or `cli` |

### The events

| Event | Carries |
|---|---|
| `claude_code.user_prompt` | `prompt_length`, `command_name`, `command_source`, and `prompt` when you turn text on |
| `claude_code.assistant_response` | `response_length`, `model`, `request_id`, `query_source`, and `response` when you turn text on |
| `claude_code.tool_result` | `tool_name`, `tool_use_id`, `success`, `result_tokens`, `skill.name`, `plugin.name` |
| `claude_code.tool_decision` | `tool_name`, `tool_use_id`, `decision`, `source`, `language` |
| `claude_code.api_request` | `model`, `endpoint`, `request_id`, `client_request_id`, `speed` |
| `claude_code.api_error` | `model`, `endpoint`, `status_code`, `error`, `client_request_id` |

Every event also carries `prompt.id`, a UUID linking all the events produced by one user prompt, along with `event.sequence` for ordering and `message.uuid` for matching back to a transcript message. A single prompt's full causal chain is reconstructable from `prompt.id` alone.

### Where attribution comes from

Cost and token metrics carry the attributes that answer the questions people actually ask.

| Attribute | Answers |
|---|---|
| `user.account_uuid`, `user.email` | Who |
| `organization.id` | Which organization |
| `model`, `speed`, `effort` | Which of <LessonLink id="A4.2" />'s dials was set |
| `agent.name` | Which subagent |
| `skill.name`, `plugin.name` | Which of the things you built in module A5 |
| `mcp_server.name`, `mcp_tool.name` | Which integration |
| `session.id`, `terminal.type`, `app.entrypoint` | Where it ran |

Team and cost-center dimensions come from `OTEL_RESOURCE_ATTRIBUTES`, which you set to whatever your organization slices by:

```bash
export OTEL_RESOURCE_ATTRIBUTES="team=payments,cost_center=eng-4471"
```

Six toggles control which of these ride along on metrics, because each distinct value multiplies your time series. `OTEL_METRICS_INCLUDE_SESSION_ID` and `OTEL_METRICS_INCLUDE_ACCOUNT_UUID` default to on; `OTEL_METRICS_INCLUDE_VERSION`, `OTEL_METRICS_INCLUDE_ENTRYPOINT`, and `OTEL_METRICS_INCLUDE_REPOSITORY` default to off; `OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES` defaults to on. Turning session id off is the usual first move when a collector bill gets uncomfortable, since it is the highest-cardinality attribute in the set and events keep it regardless.

## Walkthrough

Wire a local collector and read one cost attribution out of it.

Start a collector with an OTLP receiver on the default port and a debug exporter, saved as `otel-collector.yaml`:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    metrics:
      receivers: [otlp]
      exporters: [debug]
    logs:
      receivers: [otlp]
      exporters: [debug]
```

```bash
docker run --rm -p 4317:4317 \
  -v "$(pwd)/otel-collector.yaml:/etc/otelcol/config.yaml" \
  otel/opentelemetry-collector:latest
```

Point a session at it and give it a tag to slice by:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_RESOURCE_ATTRIBUTES="team=payments"
export OTEL_METRIC_EXPORT_INTERVAL=10000
claude
```

The shortened interval is there so the first datapoints arrive while you are still watching. Do a few turns of ordinary work, including one that dispatches a subagent, and the collector prints cost datapoints carrying their attributes:

```text
Metric #2
Descriptor:
     -> Name: claude_code.cost.usage
     -> Unit: USD
NumberDataPoints #0
Data point attributes:
     -> model: Str(claude-sonnet-5)
     -> agent.name: Str(log-summarizer)
     -> team: Str(payments)
     -> user.account_uuid: Str(...)
Value: 0.0143
```

That datapoint carries a dollar figure attributed to a model, a subagent, a team, and a person. Summed across a fleet, it answers every cost question in the problem statement.

## The two decisions that shape what you get

### Redaction is the default

Prompts, responses, and tool details are withheld unless you turn them on. Each gate is a separate variable, and each one changes what your collector is holding.

| Variable | Adds |
|---|---|
| `OTEL_LOG_USER_PROMPTS` | The text of user prompts |
| `OTEL_LOG_ASSISTANT_RESPONSES` | The text of model responses, falling back to the prompts setting when unset |
| `OTEL_LOG_TOOL_DETAILS` | Tool parameters, commands, skill and agent names, MCP details |
| `OTEL_LOG_TOOL_CONTENT` | Tool output in span events |
| `OTEL_LOG_RAW_API_BODIES` | Full request and response JSON |
| `OTEL_LOG_MANAGED_SETTINGS` | Redacted managed settings with a SHA-256 digest |

`CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH` caps the size of any logged content, defaulting to 61440 UTF-16 code units, roughly 60 KB.

An audit trail that can answer "who approved the `Bash` call that touched production" needs `OTEL_LOG_TOOL_DETAILS`, because `claude_code.tool_decision` without it tells you a decision was made and not what was decided about. Turning it on means your collector now holds the commands developers ran. That is a data-handling decision in the sense <LessonLink id="A3.4" /> means, made about a system your organization operates rather than about Anthropic's retention, and it should be made with the same people in the room.

### The administrator's lock

Telemetry configured per developer is telemetry a developer can unset. When administrators put the OTLP variables in managed settings, Claude Code removes the conflicting developer-set variables:

- Setting `OTEL_EXPORTER_OTLP_ENDPOINT` removes all per-signal endpoints.
- Setting `OTEL_EXPORTER_OTLP_PROTOCOL` removes all per-signal protocols.
- Setting any credential variable removes per-signal credentials and endpoints.

The exporter selectors, `OTEL_METRICS_EXPORTER` and `OTEL_LOGS_EXPORTER`, follow ordinary per-key precedence rather than this removal rule. <LessonLink id="A3.3" /> covers how managed settings reach a machine, and the removal behavior is what makes the destination non-optional once they arrive.

## When to use the built-in dashboards instead

Claude Code ships analytics that need no collector. Which one you get depends on how your organization signs in.

Team and Enterprise organizations have a dashboard at `claude.ai/analytics/claude-code`, visible to Admins and Owners. It shows lines of code accepted, suggestion accept rate, daily active users and sessions, a leaderboard of the top ten contributors, and CSV export. With the Claude GitHub app installed and GitHub analytics enabled, it adds contribution metrics: merged PRs and lines shipped with Claude Code assistance, attributed by matching session activity against PR diffs inside a window running from 21 days before the merge to 2 days after. Those figures are deliberately conservative. Lock files, generated code, build directories, and test fixtures are excluded, and code a developer substantially rewrote, by more than 20%, stops being attributed.

Console organizations have a dashboard at `platform.claude.com/claude-code`, gated on the UsageView permission, showing lines accepted, accept rate, activity, spend, and a per-user team insights table. Contribution metrics are not available there.

Reach for the dashboards when the question is adoption or a rough ROI story for a budget conversation. Reach for OpenTelemetry when the question is cost attribution in near real time, per-feature breakdowns, alerting, or an audit trail. Three boundaries decide it for you: contribution metrics are unavailable to organizations with Zero Data Retention enabled and to Console customers; usage on Amazon Bedrock, Google Cloud's Agent Platform, and Microsoft Foundry never reaches Anthropic, so no dashboard covers it; and the Enterprise Analytics API, which needs a key with the `read:analytics` scope, exists on Enterprise but not on Teams. OpenTelemetry has none of those boundaries, because the data never leaves your infrastructure.

## Pitfalls

**Telemetry set per developer.** Adoption looks like whoever remembered to export the variables, and cost attribution has holes shaped like your most cost-sensitive teams. Deliver the configuration through managed settings, where the endpoint and credential locks apply.

**Cardinality from `session.id`.** Your collector bill climbs faster than your Claude Code bill, because every session creates a new time series on every metric. Set `OTEL_METRICS_INCLUDE_SESSION_ID=false`; events still carry `session.id`, so per-session investigation still works.

**An audit trail with nothing in it.** `claude_code.tool_decision` arrives for every permission decision, and without `OTEL_LOG_TOOL_DETAILS` it records that a `Bash` call was allowed without recording the command. Decide whether you want the detail before an incident asks for it.

**Metrics that never appear.** Both `CLAUDE_CODE_ENABLE_TELEMETRY=1` and an exporter selection are required; setting the endpoint alone emits nothing. Set `OTEL_METRICS_EXPORTER=console` to confirm the pipeline before blaming the collector.

**Waiting a minute for the first datapoint.** The 60-second default metric interval makes a working setup look broken while you test it. Lower `OTEL_METRIC_EXPORT_INTERVAL` while you verify, then put it back.

## Try It

Prove the attribution chain end to end without a collector.

Run one session with the console exporter, which prints to your terminal:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=console
export OTEL_LOGS_EXPORTER=console
export OTEL_METRIC_EXPORT_INTERVAL=10000
export OTEL_RESOURCE_ATTRIBUTES="team=your-team-name"
claude
```

Ask a question that makes Claude read a few files, then dispatch a subagent, then wait out one export interval.

Three things should be true in the output. A `claude_code.cost.usage` datapoint carries your `team` attribute and the `model` you are running. A second cost datapoint carries an `agent.name` for the subagent, separating its spend from the main conversation. And a `claude_code.tool_decision` event records each permission decision with a `decision` and a `source`, with no command text in it.

Then turn on one gate and watch the same event change shape:

```bash
export OTEL_LOG_TOOL_DETAILS=1
```

Run the same work again. The tool events now carry the parameters. Decide, before you move this to a shared collector, whether that is a trail you want your organization to hold.

## FAQ

**Does telemetry work on Amazon Bedrock and the other cloud providers?** Yes, and it is the only option there. Claude Code does not send metrics from a cloud provider back to Anthropic, so the analytics dashboards and the Claude Code Analytics API do not cover that usage. The exporter runs on the developer's machine and is unaffected.

**Can I get per-user cost without OpenTelemetry?** Partly. Team and Enterprise organizations can export a spend report CSV listing token usage and estimated spend per user and per model, updated daily, and Console organizations have the Console dashboard and the Claude Code Analytics API. OpenTelemetry is the only one that streams in near real time and the only one that breaks cost down by skill, plugin, or MCP server.

**What links the events from one prompt together?** `prompt.id`, a UUID on every event produced by a single user prompt, with `event.sequence` giving the order within a process. A query grouping on `prompt.id` reconstructs one turn: the prompt, each tool decision, each tool result, the API requests, and the response.

**Are contribution metrics available under Zero Data Retention?** No. An organization with ZDR enabled sees usage metrics only on the dashboard. <LessonLink id="A3.4" /> covers the wider set of features ZDR removes.

**How do I separate automation spend from interactive work?** `query_source` on the cost and token metrics distinguishes where a request came from, and `app.entrypoint` records the launch method, including `cli`, `sdk-ts`, and `sdk-py`. Enable `OTEL_METRICS_INCLUDE_ENTRYPOINT` to get the latter on metrics as well as events.
