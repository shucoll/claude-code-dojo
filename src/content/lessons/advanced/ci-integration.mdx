# CI integration

After the sprint, PulseBoard's standards still hold only when someone runs Claude on a laptop. This milestone moves Claude into the repository itself: an issue can summon it, every pull request meets an automated reviewer, and a security reviewer watches every change Claude writes, locally or in CI.

## Goal for this stage

Wire `@claude` to PulseBoard's issues through GitHub Actions, deploy an automated review layer on pull requests, add the security-guidance plugin as a second lens, and write PulseBoard's review priorities where your review layer will read them. The graded part is a written justification in a new `RUNBOOK.md`: which review layer you chose, what it misses, what it costs, and where its policy lives.

Two of the layers are gated by plan. Code Review needs Team or Enterprise, ultrareview needs a claude.ai sign-in, and neither is available to an organization with Zero Data Retention (<LessonLink id="A2.3" />). Every plan can build the third path, a review job in your own GitHub Actions, and it reaches the same artifact: review comments on every pull request. The justification is graded the same way on every path.

**Environment:** your PulseBoard repository on GitHub, private as you created it in <LessonLink id="I8.1">I8.1</LessonLink>, with the <LessonLink id="A7.1">A7.1</LessonLink> work merged to `main`. You need admin access to it, the GitHub CLI authenticated, and either a Claude API key or a Claude subscription to generate a token from.

## Steps

### 1. Pick the review layer and write down why

Choose the layer that reviews PulseBoard's pull requests before you install anything, because the choice decides which files you write in step 5.

| Layer | Runs on | Available on | Cost | Reads your review policy from |
|---|---|---|---|---|
| Code Review | every pull request, per the trigger you set | Team and Enterprise, without ZDR | $15 to $25 per review, billed as usage credits | `REVIEW.md` and `CLAUDE.md` |
| Ultrareview | the pull requests you choose, when you run it | a claude.ai sign-in, without ZDR | $5 to $25 per review as usage credits, after three free runs on Pro and Max | nothing documented beyond the change itself |
| The action running the `code-review` plugin | every pull request, per the workflow's triggers | every plan | GitHub Actions minutes plus tokens | `CLAUDE.md` files only |

On Team or Enterprise, the real choice is between the first two rows: every pull request reviewed on a trigger, or a deeper, verified review on the pull requests you judge risky. Everywhere else, the third row is your pull request layer, and ultrareview can still sit on top of it as an escalation if you sign in with claude.ai.

Start `RUNBOOK.md` at the repository root. Later milestones add to it, and by the end of the module it is how someone else operates PulseBoard. Its first section records this decision:

```markdown
# PulseBoard runbook

## CI and review

### Review layer
- Layer, and the plan fact that decided it:
- What it structurally misses, and which other layer covers that:
- Monthly cost at our pull request rate:
- Where its review policy lives, and what that policy cannot change:
```

Fill in the first line now and the rest as you build. For the cost line, count last month's pull requests with `gh pr list --state merged --search "merged:>=YYYY-MM-DD" --limit 200 --json number --jq length`, using the date a month ago, and multiply by the per-review figure for your layer.

### 2. Connect the repository

Every path uses the Claude GitHub App, and the issue workflow in step 3 needs a credential. From a Claude Code session in the repository:

```prompt
/install-github-app
```

After it installs the app, choose **Skip for now**. You will write the workflow files yourself, because the generated ones lack the setup step PulseBoard needs. Then store the credential as a repository secret:

```bash
gh secret set ANTHROPIC_API_KEY
```

On a subscription instead, run `claude setup-token`, store the result with `gh secret set CLAUDE_CODE_OAUTH_TOKEN`, and in each workflow below replace the `anthropic_api_key` line with `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}`. The token draws on the subscription of whoever generated it, so the runbook should name that person.

### 3. Wire `@claude` to issues

Save `.github/workflows/claude.yml`:

<WhenLang is="javascript">

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened]
jobs:
  claude:
    if: |
      (github.event_name == 'issues' && (contains(github.event.issue.body, '@claude') || contains(github.event.issue.title, '@claude'))) ||
      (github.event_name != 'issues' && contains(github.event.comment.body, '@claude'))
    runs-on: ubuntu-latest
    timeout-minutes: 30
    concurrency:
      group: claude-${{ github.event.issue.number || github.event.pull_request.number }}
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-plugins-official.git"
          plugins: "security-guidance@claude-plugins-official"
          claude_args: "--model sonnet --max-turns 30"
```

The trigger and permission lines are the ones <LessonLink id="A2.2" /> walked through, plus `issues: opened`, so a new issue that mentions `@claude` in its title or body starts a run without a separate comment. Three additions are specific to PulseBoard.

The dependency install is there because the checkout brings the repository's own `.claude/` configuration with it. The `Stop` gate from <LessonLink id="I8.4" /> runs the test suite before Claude may finish, the formatter runs after every edit, and the migration guard still refuses edits to shipped migrations. That is the behavior you want from Claude in CI, and it only works on a runner where the tests can run. Without the install step, the `Stop` gate finds a red suite on every attempt, keeps sending Claude back, and spends turns until the cap ends the run.

The plugin inputs install the security-guidance plugin on the runner, so the second lens from step 6 also watches the code Claude writes for an issue.

The limits bound what one mention can cost: 30 turns, 30 minutes, Sonnet, and one run at a time per issue or pull request.

Loading the repository's configuration is safe on this repository because it is private and the action starts only for users with write access. On a public repository, weigh the `--bare` trade-off from <LessonLink id="A2.2" /> before copying this file.

### 4. Deploy the pull request layer

Build the path you chose in step 1.

#### Code Review

An Owner of your Claude organization opens the Claude Code admin settings, finds the Code Review section, and runs **Setup**. Select the PulseBoard repository and set its Review Behavior to **Once after PR creation**. After every push multiplies the cost by the number of pushes, and a small team's pull requests rarely need more than one automatic pass: anyone with write access can comment `@claude review` for another. Then set a monthly spend cap for the Code Review service under the organization's usage settings, before the first bill decides it for you.

#### Ultrareview

There is nothing to install. Decide which pull requests earn a review, and write the rule into the runbook. For PulseBoard a sound rule is any pull request that touches `data/` or `migrations/`, since those hold the GitHub access, the cache, and the one kind of change the project cannot take back. On such a pull request, the reviewer runs:

```prompt
/code-review ultra 42 --post
```

`--post` preselects posting the verified findings to the pull request as a comment from your GitHub account, and the launch dialog shows the estimated cost before you confirm. Keep the session open until the review finishes, or nothing is posted.

#### The action running the `code-review` plugin

Save `.github/workflows/claude-code-review.yml`:

<WhenLang is="javascript">

```yaml
name: Code Review
on:
  pull_request:
    types: [opened, ready_for_review]
jobs:
  review:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    concurrency:
      group: review-${{ github.event.pull_request.number }}
      cancel-in-progress: true
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
```

This is the review workflow from <LessonLink id="A2.2" /> with three changes. The install step is there for the same reason as in `claude.yml`, since the `Stop` gate runs at the end of a review too. The concurrency group cancels a review that a newer event has already superseded.

The trigger list is shorter than the documented example, and the plugin itself is the reason. Its first step skips any pull request that already carries a comment from Claude, so after the first review every `synchronize` run starts a runner only to stop. Triggering on `opened` and `ready_for_review` pays for the reviews that happen. To get a second review after a large rework, delete Claude's earlier comment and mark the pull request ready again.

### 5. Write the review policy where your layer reads it

PulseBoard's priorities are the same on every path. Important means something that breaks behavior or leaks the token: a route reaching GitHub or SQLite directly, the token logged or returned, an edit to a shipped migration, GitHub-sourced text rendered as HTML, a new endpoint without a test. Everything else is minor, and anything a formatter or the test suite already enforces is noise. What changes by path is the file those priorities go in.

<WhenLang is="javascript">

On the Code Review path, write `REVIEW.md` at the repository root:

```markdown
# Review instructions

## What Important means here

Reserve Important for:
- a route in routes/ that calls Octokit or SQLite directly instead of a data/ module
- the GitHub token logged, returned in a response, or passed as an argument
- any edit to a migration that already exists on main
- text from GitHub (issue titles, labels, release names) rendered with innerHTML
- a new endpoint without a test in tests/ that mounts only its own router

Everything else is Nit at most.

## Cap the nits

Report at most three Nits. Summarize the rest as "plus N similar".

## Do not report

- Formatting: a hook formats every edit
- package-lock.json, SPRINT.md, and RUNBOOK.md

## Always check

- A data/ function reads the SQLite cache before it calls GitHub
- Response shapes match the contract in SPRINT.md

## Re-reviews

After the first review of a pull request, post Important findings only.
```

</WhenLang>

Test it on a real pull request. Local `/code-review` never reads `REVIEW.md`, so testing it there proves nothing either way.

On the action path, the plugin decides what reaches you. Its reviewers look for the root `CLAUDE.md` and any `CLAUDE.md` in a directory the pull request touches, flag only rule violations they can quote from those files, and post no style findings or nits at all ([the plugin's instructions](https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md)). Three consequences for PulseBoard:

- Most of the priorities are already quotable. The root `CLAUDE.md` says every endpoint ships with a test, that data access goes through `data/`, and that the token comes from the environment.
- The data-access rule in `.claude/rules/` is not in the files the plugin looks for, so anything only that rule says is invisible to the reviewer.
- Severity, the nit cap, and skip rules have no setting on this path. The plugin's own filter already posts only high-confidence findings, and your runbook should say so.

Put the two priorities the root file lacks next to the code they govern. Create `public/panels/CLAUDE.md`:

```markdown
Panel scripts render text from GitHub (issue titles, labels, release names) with textContent. Never assign it to innerHTML.
```

And `data/CLAUDE.md`:

```markdown
Every function here reads the SQLite cache before it calls GitHub.
```

A directory `CLAUDE.md` also loads in your own sessions when Claude reads files in that directory, so the rule reaches the author before it reaches the reviewer.

On the ultrareview path, use the action path's two directory files. They guide every Claude session that works in those directories, which is where most of PulseBoard's changes are written.

Whichever file you wrote, fill in the runbook's last line: where the policy lives, and what that path gives you no way to change.

### 6. Add the security lens

The review layer sees a finished pull request. The security-guidance plugin works earlier, while Claude writes the code, on every plan. Enable it for everyone who works on PulseBoard by adding it to `.claude/settings.json`:

```json
{
  "enabledPlugins": {
    "security-guidance@claude-plugins-official": true
  }
}
```

The workflow in step 3 already installs it on the runner. Its guidance file is what tunes it to PulseBoard. PulseBoard renders text that anyone who can open an issue controls, and it holds a token that can read your repositories, so tell the model-backed reviews that. Create `.claude/claude-security-guidance.md`:

```markdown
# Security guidance for PulseBoard

- Issue titles, label names, and release names are attacker-controlled on any repository with outside contributors. Panel scripts must render them as text, never as HTML.
- The GitHub token is read from the environment in data/github only. Flag any code that logs it, returns it, or passes it to another function.
- Query parameters such as days and count are bounded integers. Flag a route that passes one to GitHub or SQLite without validating it.
- SQLite queries use bound parameters. Flag any SQL built by string concatenation.
```

Add one deterministic pattern for the per-edit check. Save it as `.claude/security-patterns.json`, since the YAML form needs PyYAML and the JSON form works on any Python:

```json
{
  "patterns": [
    {
      "rule_name": "github_token_literal",
      "substrings": ["ghp_", "github_pat_"],
      "exclude_paths": ["**/.claude/security-patterns.json"],
      "reminder": "This looks like a GitHub token. PulseBoard reads GITHUB_TOKEN from the environment only."
    }
  ]
}
```

The `exclude_paths` entry keeps the rule from firing on the file that defines it. Note in the runbook what this lens cannot do: its findings reach Claude as instructions and never block a write or a commit. The blocking still comes from the hooks you wrote in <LessonLink id="I8.4" />.

Commit everything and push to `main`. Issue and comment events run the workflow file from the default branch, so nothing answers `@claude` until it is there:

```prompt
Commit the workflows, the review policy files, RUNBOOK.md, and the security-guidance settings with a message describing the CI setup, then push.
```

### 7. Run it end to end

Open an issue on PulseBoard that summons Claude:

```bash
gh issue create --title "@claude add a label filter to the stale-issue view" \
  --body "GET /api/stale should accept an optional label query parameter and return only stale issues carrying that label. Add a test."
```

Watch the run in the Actions tab. Claude's comment on the issue updates as it works, and the run should end with a branch or a pull request for the change, with the suite green, because the `Stop` gate would not have let it finish otherwise.

When the pull request is open, your review layer takes over: a **Claude Code Review** check run on the Code Review path, a review comment from the workflow on the action path, or your own `/code-review ultra` run with `--post`. If the action path's run fails its actor check because a bot opened the pull request, that is the bot rejection from <LessonLink id="A2.2" />: add the bot to `allowed_bots` in the review workflow and record it in the runbook.

Read what the review found. Then complete the runbook's review section, and add a short section on how to turn each piece off: which workflow file to delete, where the Code Review toggle lives, which secret to remove, and which key to revoke in the Console.

## The artifact

At the end of this stage you have:

- A `claude.yml` workflow that answers `@claude` in issues and pull requests, with the project's hooks running on the runner and hard limits on turns, time, and concurrency.
- A pull request review layer: Code Review enabled with a spend cap, an ultrareview rule in the runbook, or a `claude-code-review.yml` workflow triggered on `opened` and `ready_for_review`.
- PulseBoard's review priorities written where that layer reads them: `REVIEW.md`, or directory `CLAUDE.md` files beside the code they govern.
- The security-guidance plugin enabled for the project and the runner, with a PulseBoard guidance file and a token pattern.
- A `RUNBOOK.md` whose first section records the review layer, what it misses, what it costs, where its policy lives, and how to switch everything off.

**Done looks like:** an issue that mentions `@claude` produces a change with a green suite, the resulting pull request receives a review from your chosen layer, and someone reading only `RUNBOOK.md` could say why that layer was chosen and what it costs per month.

## Reasoning recap

Review layers compose when each one watches a moment the others cannot. Choosing a single layer is choosing which moments go unwatched, so the justification names the gap and the layer that covers it.

Before trusting a reviewer to enforce a rule, find out which files it reads.

Moving Claude into CI moves your configuration with it. From here on, treat every hook and permission you wrote for your own sessions as CI behavior too, and give the runner whatever those hooks need to run.
