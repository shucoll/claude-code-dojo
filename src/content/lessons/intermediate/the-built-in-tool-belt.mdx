# The built-in tool belt

## The problem

Back in <LessonLink id="B1.1" /> we said Claude Code "uses tools" and left it there. You have been reading those tools scroll past ever since: a line appears, Claude does something, sometimes a prompt interrupts and sometimes it doesn't. Most of the time it works, so you stopped looking.

That gap is now costing you. To write permission rules, restrict a subagent, or match a hook, you have to name tools exactly, and to trust the agent you have to read what it is doing turn by turn instead of hoping. This lesson closes the gap: the complete belt, what each tool can and cannot break, and the one thing that predicts every permission prompt you have ever clicked through.

## The concept

Claude has a fixed set of built-in tools. It chooses which to use; you almost never name one while working. Every tool falls into a **risk tier**, and the tier predicts the prompt.

There are four tiers, plus one special case:

- **Read-only** reads your code and never changes it. Runs without asking.
- **Writes files** changes files on disk. Asks first.
- **Runs commands** executes shell commands, which can do anything your terminal can. Asks first.
- **Leaves your machine** reaches the network. Asks first, per domain.
- **Delegation** (the `Agent` tool) hands work to a subagent. Launching it never prompts; the subagent's own tool calls are checked as they happen.

Every permission prompt in <LessonLink id="B1.3" /> was one of these tools stopping at its gate. Learn the tiers and you can predict, before Claude acts, whether the next step will interrupt you.

### Read-only: it looks, it never touches

These four gather information and change nothing. Inside your project folder they run without a prompt, which is why most of a session scrolls by uninterrupted.

- **`Read`** opens a single file and returns its contents with line numbers. It also reads images, PDFs, and notebooks. What it can "break" is only your context budget: pointed at a huge file it spends tokens, and pointed at `.env` it will read your secrets like any other file (the hygiene point from <LessonLink id="B1.3" />).
- **`Grep`** searches inside files for a pattern, built on ripgrep. It skips gitignored files by default.
- **`Glob`** finds files by name pattern, like `src/**/*.ts`. Unlike Grep, it does *not* skip gitignored files.
- **`LSP`** is code intelligence from a language server: jump to a definition, find references, surface type errors after an edit. It stays inactive until you install a code-intelligence plugin for your language.

One platform split to expect. On Windows, `Grep` and `Glob` are part of the default tool set. On macOS, Linux, and WSL they are left out of it, and Claude searches with `grep` and `find` through Bash instead, so those searches reach your transcript, your permission rules, and your hook matchers as `Bash` calls. Searching is read-only in either form, so neither one prompts.

In a transcript they look like this:

```text
⏺ Grep(pattern: "useState", glob: "**/*.tsx")        # Windows
  ⎿ Found 12 files

⏺ Bash(grep -rl "useState" --include="*.tsx" src)    # macOS, Linux, WSL
  ⎿ Found 12 files

⏺ Read(src/components/Counter.tsx)
  ⎿ Read 43 lines
```

No prompt appeared because nothing changed. Read, Grep, and Glob do still prompt when a path sits *outside* your project and additional directories.

### Writes files: the first gate

These change files on disk, so each one asks before it acts (in manual mode; auto mode approves edits inside your working directory without asking).

- **`Edit`** does an exact find-and-replace inside one file: the text it is replacing must match character for character and appear exactly once. Claude normally has to have read the file first, though newer models can skip that when reading it would not have prompted anyway. What it can break is the file it edits, if the replacement is wrong.
- **`Write`** creates a new file or overwrites an existing one with entire new contents. It does not merge or append. Overwriting an existing file follows the same read-first rule as `Edit`, and for notebooks and partially read files the read is always required.
- **`NotebookEdit`** edits one Jupyter notebook cell at a time. Its permission rules use the same path format as `Edit`.

```text
⏺ Edit(src/checkout.ts)
  ⎿ Claude wants to edit src/checkout.ts
     - const rate = 0.1
     + const rate = TAX_RATE

     ❯ 1. Yes
       2. Yes, and don't ask again this session
       3. No, tell Claude what to do differently
```

The prompt names the tool's target. Approving an edit lasts until the session ends, then Claude asks again, as <LessonLink id="B1.3" /> described.

### Runs commands: the widest tool

- **`Bash`** runs shell commands. This is the most capable and the most dangerous tool on the belt, because it can do anything your terminal can: run tests, install packages, delete files, push to git, call the network. Two rules decide when it prompts. First, Bash runs a built-in set of read-only commands (`ls`, `cat`, `git status`) *without* a prompt. Second, anything with side effects prompts, and the prompt shows you the command.
- **`PowerShell`** is the same idea for PowerShell, native on Windows and opt-in elsewhere.
- **`Monitor`** runs a command in the background and reacts to its output (tailing a log, polling CI). It obeys the same permission rules as Bash.

```text
⏺ Bash(git status)
  ⎿ On branch main, working tree clean

⏺ Bash(npm run build)
  ⎿ Claude wants to run npm run build

     ❯ 1. Yes
       2. Yes, and don't ask again for npm run build
       3. No, tell Claude what to do differently
```

The first command read state and ran silently; the second has consequences and stopped. Notice that "don't ask again" for a shell command is remembered permanently for that command in that project, unlike a file edit. Claude Code stores that approval as a <LessonLink id="I1.2">permission rule</LessonLink>, which you can also write by hand.

### Leaves your machine: the network tier

- **`WebFetch`** takes a URL and a question, fetches the page, and answers the question using a small fast model. It is lossy by design: Claude receives the model's answer, not the raw page. It prompts before each fetch unless your rules already allow the domain (a preapproved set of documentation sites is exempt).
- **`WebSearch`** runs a web search and returns result titles and URLs. It does not read the pages; Claude follows up with `WebFetch` to read one.

```text
⏺ WebFetch(https://example.com/changelog)
  ⎿ Claude wants to fetch example.com

     ❯ 1. Yes
       2. Yes, and don't ask again for example.com
       3. No
```

The "don't ask again" option names the domain, not the full URL: choosing it lets later fetches from that domain run without a prompt.

### Delegation: the tool that hides a whole session

**`Agent`** hands a task to a subagent that runs in its own separate context window and returns a single result. Launching it does not prompt. The subagent then uses these same tools, and *its* calls are checked against your rules as they happen. The catch for reading transcripts: you see the launch and the final result, not the subagent's intermediate work, which stays in its own transcript. A short `Agent(...)` line can represent a great deal of activity you did not watch. Subagents get <LessonLink id="I6.1">their own module</LessonLink> later.

### The long tail

Beyond these, the belt carries a set of session-control tools: task-list and scheduling tools, plan-mode toggles, MCP resource readers, and so on. They manage the session rather than your code, most run without a prompt, and you never need to memorize them. One you will meet later is `Skill`, which runs a skill (<LessonLink id="I3.1">Module I3</LessonLink>). When a real tool matters, its own lesson introduces it.

## Reading the prompt: tool to tier

When a prompt appears, its first words name the tool, and the tool names the tier:

| The prompt says | Tool | Tier | What it wants to do |
|---|---|---|---|
| "wants to edit …" | `Edit` / `Write` | Writes files | change a file on disk |
| "wants to run …" | `Bash` | Runs commands | execute a shell command |
| "wants to fetch …" | `WebFetch` | Leaves your machine | reach a URL |
| (no prompt) | `Read` / `Grep` / `Glob` | Read-only | look, without changing anything |

With the tiers learned, you can read a transcript the way you read a diff: spot the two or three lines that actually did something and confirm they were what you asked for.

## Checking your belt

Your exact tool set depends on your provider, platform, and settings, so the reliable way to see what a running session has is to ask:

```prompt
What tools do you have access to?
```

Claude answers with a plain-language summary. For the exact names of tools added by MCP servers (<LessonLink id="I5.1">Module I5</LessonLink>), run:

```prompt
/mcp
```

You need this when a tool you expected is missing (a subagent restricted it, a deny rule removed it, or your platform never had it) and you want to confirm what is actually loaded.

## Pitfalls

These are all misreadings of a transcript.

- **"No prompt appeared, so nothing happened."** Read-only tools and Bash's read-only commands run silently by design. Silence means the action was safe, not that it was skipped. Look for the result line, not the prompt.
- **"It read `.env`, my secrets are compromised."** Reading a file changes nothing on disk. It does put the file's contents into the conversation, the same exposure as pasting a secret in, so if Claude should never see a file, deny reading it with a rule like `Read(.env)`.
- **"WebFetch says the page doesn't mention X, so it doesn't."** WebFetch returns a fast model's answer to a specific question, not the page. A "no" often means the extraction prompt did not ask the right thing. Have Claude fetch again with a sharper prompt, or read the raw page another way.
- **"My search found nothing, so the code isn't there."** `Grep` skips gitignored files; `Glob` does not. A Grep that comes up empty may simply be ignoring a gitignored file where the match lives.
- **"The `Agent` line finished instantly, so it did nothing."** Subagents start in the background by default, so the `Agent` line returns as soon as the subagent launches. Its result reaches Claude in a later turn.

## Try It

**Environment:** any scratch directory or a small public repo you have cloned (for example a docs site or a starter template). Nothing here writes to your code, so no branch or commit is needed first.

1. Start Claude and ask, `What tools do you have access to?` Read the answer and sort the names into the four tiers in your head. Anything you cannot place is probably a session-control tool from the long tail.
2. Ask Claude to find something: `Where is the main entry point defined?` Watch the transcript. Which tool fired: `Grep`, `Glob`, or a `grep`/`find` search through `Bash`? Did it prompt? (It should not.)
3. Ask it to run a read-only command like `git status`, then something with a side effect like running the test suite. Confirm the first ran silently and the second named `Bash` in a prompt.
4. Ask it to fetch a page from a site that is not a documentation site (many documentation sites are preapproved and fetch without asking). Confirm the "don't ask again" option names the domain, not the full URL.

**Success criteria:** for any tool call you saw, you can state its tier, and before Claude takes its next step you can predict whether it will prompt.

## FAQ

**Do I ever call these tools myself?** No. Claude chooses them while working. You name tools directly only when you configure the agent: in permission rules, in a subagent's tool list, and in hook matchers. Those are the next several lessons.

**Why did `Read` prompt me once?** The path was outside your project and additional directories. Inside them, Read, Grep, and Glob are silent; outside, they ask first.

**What are all the tools my summary listed that aren't on the map?** Session-control tools: task lists, scheduling, plan mode, MCP resource access. They act on the session, not your code, and mostly run without a prompt. The map deliberately shows only the tools whose behavior you need to read.

**Is a skill a tool?** A skill runs *through* the built-in `Skill` tool rather than adding a new tool of its own. You will build skills in <LessonLink id="I3.1">Module I3</LessonLink>.

**How do I turn a tool off entirely?** Add its name to a `deny` rule in your permission settings. That is the mechanism the next lesson, on <LessonLink id="I1.2">permission rules</LessonLink>, is built on.
