# Agent teams: preview

Subagents gave you parallel work in <LessonLink id="I6.3" />: fan out several, each in its own window, each reporting back to you. Agent teams are a structurally different way to run many Claudes at once.

## The concept

An agent team is several Claude Code sessions working as peers, sharing a task list and messaging each other directly. The task list needs the Task tools, which newer models, including the current default, leave out until you opt in with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`.

One session is the lead. It spawns the others, but it does not sit between them: teammates claim tasks off a shared list, talk to each other, and challenge each other's findings without routing through the lead. Compare that to a subagent, which is an isolated delegate that returns its result to whoever spawned it. A subagent Claude named can be messaged by name afterwards, but there is no shared list to claim work from.

## Against subagents

| | Subagents | Agent teams |
|---|---|---|
| **Context** | own window; result returns to the caller | own window; fully independent |
| **Communication** | returns a result to the caller; named subagents can also message each other | teammates message each other directly |
| **Coordination** | the caller manages all work | self-coordination by message, plus a shared task list for agents with the Task tools |
| **Best for** | focused work where only the result matters | work that needs discussion between the workers |
| **Token cost** | lower; the result is summarized back | higher; each teammate is a full Claude instance |

The deciding row is coordination. If your parallel workers never need to hear from each other, subagents already do the job, more cheaply. The moment the workers need to claim work off a shared list and challenge each other without the caller in the loop, you need a team.

## Why it costs more

A subagent spends tokens, then hands you a summary and stops. That summary is the compression <LessonLink id="I2.1" /> credited delegation for.

A team removes that compression. Every teammate is a separate, full Claude session with its own context window, running for as long as the team does, and messages between them are more tokens on top. Cost scales with the number of active teammates, roughly linearly. Five teammates is close to five sessions' worth of spend.

## When to care

The tasks that justify the cost share a shape: independent enough to parallelize, but interdependent enough that the workers benefit from talking.

- **Parallel review.** Three teammates on one PR, one per lens (security, performance, tests), synthesized by the lead. A single reviewer drifts toward one kind of issue; split across three teammates, each lens gets full attention.
- **Competing hypotheses.** A confusing bug handed to several teammates told to disprove each other, like a scientific debate. Sequential investigation anchors on the first plausible theory; in a debate, the theory that survives is more likely to be the root cause.
- **Cross-layer features.** Frontend, backend, and tests, each owned by a teammate who will not touch the others' files.

Reach for a single session or subagents instead when the work is sequential, edits the same files, or carries many dependencies. Coordination overhead is real, and three focused teammates beat five scattered ones.

The feature is experimental and off by default; you turn it on with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in settings or the environment, and it carries live limitations around resuming sessions and shutting teammates down. Flipping it on also changes plain delegation: a subagent Claude names then launches as a teammate, so a team can form when you never asked for one. The default answer to "should I use this today?" is usually no: the work has to genuinely need workers that talk to each other before the token bill and the coordination are worth it.
